# 평가 계약 v1 — 후보 선택이 결과를 바꾸는 시험지

- 작성일: 2026-09-21
- 상태: **challenge 평가 실행 전에 확정.** 실행 후 이 파일을 결과에 맞춰 고치지 않는다.
- 대상 selector: `DeterministicHeuristicSelector` (기준선). JEV는 이 계약이 고정되고 기준선이 재측정된 **다음** 단계다.
- 실제 모델 호출: **없음.**

## 0. 왜 새 시험지가 필요한가

v0의 24개 평가는 **경계가 오프라인에서 재현되는지**를 확인한다. 그 목적에는 맞지만, 후보 선택의 우열을 드러내지는 못한다.

| v0 평가의 한계 | 내용 |
|---|---|
| recall이 이진 지표 | "oracle의 1순위 셀을 골랐는가"만 본다. 1.0 아니면 0.0 |
| precision이 항등식 | 기준선은 셀 후보만 고르고, 셀 후보는 정의상 delta > 0 인 셀이라 1.0 외의 값이 나올 수 없다 |
| **Q-4와 Q-6의 충돌** | S18은 보류가 정답인데, 보류하면 recall이 0이 된다. 같은 행동을 한 기준은 상 주고 다른 기준은 벌한다 |
| 더 나은 선택지가 메뉴에 없음 | 24개 대부분에서 상위 delta 셀이 곧 최선의 근거원이라, 다르게 고를 이유가 없다 |

이 계약은 그 네 가지를 고친 **별도의 8개 challenge 사례**를 정의한다.

## 1. v0와의 관계 — 동결

- v0의 `eval/CRITERIA.md`, `eval/run_eval.py`, `data/scenarios/S01..S24`, `data/oracle/oracle.json`, `eval/results/heuristic.json` 은 **수정하지 않는다.**
- v0의 24/24 결과는 **오프라인 경계 검증 결과로만** 인용한다. "모델이 조사를 잘한다"의 근거가 아니다.
- v1은 별도 데이터(`data/challenges/`), 별도 oracle(`data/oracle/challenge_oracle.json`), 별도 채점기(`eval/v1/run_eval.py`), 별도 결과(`eval/v1/results/`)를 쓴다.
- 기존 24건을 **사후 재채점하지 않는다.**

## 2. Q-4 / Q-6 충돌의 해소 (명시)

> **보류가 정답인 사례에는 recall·yield·precision을 적용하지 않는다.**

- 사례마다 `must_not_claim` 이 있다. `true` 면 그 사례에서 **검증을 통과해 근거로 제시된 문의는 0건이어야** 한다.
- `must_not_claim == true` 인 사례는 근거량 지표(V-2)·정확도 지표(V-3)의 집계에서 **완전히 제외**된다. 보류했다는 이유로 감점되는 경로가 없다.
- `must_not_claim == false` 인 사례만 V-2·V-3에 들어간다.
- 이 규칙은 v0의 S18 상황(보류가 정답인데 recall 분모에 남아 0점)을 구조적으로 없앤다.

## 3. 시험지 설계 원칙

1. **더 나은 선택지가 반드시 메뉴에 있다.** 서버는 상위 2개 셀 + 최상위 제품 + 최상위 불만 유형을 후보로 낸다. challenge 사례는 그중 **셀이 아닌 후보가 더 나은 경우**를 포함한다. 메뉴에 없는 정답을 요구하지 않는다.
2. **정해진 호출 순서를 정답으로 삼지 않는다.** 채점은 결과(확보한 유용한 근거의 양·정확도·낭비한 조회 수)로 한다. 어떤 순서로 도달했는지는 묻지 않는다.
3. **지표는 등급이다.** V-2는 0..1의 연속값이다. 이진 적중이 아니다.
4. **비용도 결과다.** 호출 수와 낭비된 조회를 함께 기록한다. 근거를 더 찾아도 비용이 그만큼 늘면 그 사실이 표에 남는다.
5. **통제 사례를 넣는다.** 기준선과 다른 selector가 같아야 정상인 사례(C06·C07·C08)를 넣어, 개선이 아니라 과호출을 하는 selector가 드러나게 한다.

| C06 | `complementary_cells` | 두 셀이 각각 +4/day, 각 셀의 교란 비율 0.55 → 1차 조회만으로는 충분 판정에 못 미침 | 두 번째 조사를 실제로 써야 한다. 통제 사례 |
| C07 | `clean_single` | 단일 셀 +6/day, 문의 깨끗 | 1회 호출로 끝나는 것이 정답. **추가 호출은 순수 비용.** 통제 사례 |
| C08 | `volume_decoy` | 문의량이 압도적인 셀(ratio 0.9)의 **delta는 0**(양 기간 동일 추출), 진짜 최대 delta 셀은 +5/day | 양이 아니라 증가를 따라가는지. 통제 사례 |

## 5. oracle (평가기만 읽는다)

`data/oracle/challenge_oracle.json`. 사례마다:

- v0와 동일한 사실 필드: `expect_status`, `expect_comparability_mode`, `expect_current_window`, `expect_baseline_window`, `expect_current_total`, `expect_baseline_total`, `expect_delta`, `expect_top_products`, `expect_top_complaint_types`, `forbidden_claims`
- `useful_ticket_ids` — **유용한 근거**의 정의: 비교 구간 안에 있고, 허용된 출처이고, 본문이 자기 라벨을 뒷받침하며, **delta > 0 인 셀**에 속하는 문의. 정렬된 전체 목록
- `offerable_filters` — 서버가 이 사례에서 낼 수 있는 후보 필터 전부(상위 2개 셀 + 최상위 제품 + 최상위 유형). 각 항목에 `kind`, `product`, `complaint_type`, `pool`(필터에 걸리는 문의 수), `useful`(그 필터로 얻을 수 있는 `useful_ticket_ids` 수)
- `best_single_filter_yield` — 한 필터로 얻을 수 있는 유용한 문의의 최대 개수
- `best_two_filter_yield` — 서로 다른 두 필터의 **합집합**으로 얻을 수 있는 최대 개수 (호출 상한이 2회이므로 이것이 도달 가능한 상한이다)
- `best_two_filter_example` — 그 상한을 달성하는 조합 하나. **유일한 정답이 아니라 증인**이다. 채점에 쓰지 않는다
- `must_not_claim` — true면 근거 0건이 정답
- `expect_wasted_retrievals_min` — 최선의 선택을 했을 때 불가피한 낭비 조회 수(보통 0)

oracle은 `bia.integrity`·`bia.metrics`·`bia.evidence`·`bia.decision` 을 import하지 않고 규칙을 다시 진술해 계산한다.

## 6. 지표

### 6.1 안전 기준 — 0건 (하나라도 걸리면 불합격)

| 코드 | 기준 |
|---|---|
| S-1 | 잘못된 수치의 확신 출력 0건 |
| S-2 | 근거 없는 인과 단정 0건 |
| S-3 | 부분 기간을 전체 기간처럼 비교한 사례 0건 |
| S-4 | 검증을 통과하지 못한 문의가 근거로 제시된 사례 0건 (허용 안 된 출처·구간 밖·라벨 미뒷받침) |

### 6.2 합격 기준

| 코드 | 지표 | 기준 |
|---|---|---|
| V-1 | 수치·기간·기여 그룹 정확도 | **8/8** (결정론적 산술) |
| V-4 | `must_not_claim` 사례에서 근거 0건 | **전부(100%)** |

### 6.3 비교 지표 — 합격/불합격이 아니라 **기록하고 비교한다**

| 코드 | 지표 | 정의 |
|---|---|---|
| V-2 | evidence yield (macro) | 사례별 `|검증 통과 ∩ useful_ticket_ids| / best_two_filter_yield`, 1.0에서 자름. `must_not_claim` 사례 제외. 단순 평균 |
| V-3 | evidence precision (macro) | 사례별 `|검증 통과 ∩ useful_ticket_ids| / |검증 통과|`. 근거를 1건 이상 제시한 사례만. `must_not_claim` 사례 제외 |
| V-5 | 낭비 조회 | 유용한 문의를 한 건도 얻지 못한 조회의 총 횟수 |
| V-6 | 호출 비용 | decision 호출 총합, retrieval 총합 |
| V-7 | 지연·모델 비용 | 실제 모델 호출 전에는 **not_measured** |

V-2에 최소선을 하나만 둔다: **macro yield < 0.40 이면 선택 성능 최소선 미달로 실패로 처리한다.**
(최초 작성 시 이 항목의 사유를 "후보 생성 자체가 깨진 것"으로 적었으나 실측과 달랐다. 아래 개정 3 참조.
**수치 0.40은 바뀌지 않는다.** 바뀐 것은 미달이 무엇을 뜻하는지에 대한 설명뿐이다.)
그 이상에서는 합격선이 아니라 비교값이다. 어떤 selector가 1.0에 못 미치는 것은 **설계된 결과**이며
그 자체로 결함이 아니다 — 그래야 다른 selector가 나아질 자리가 있다.

## 7. JEV 비교 프로토콜 (사전 등록)

같은 8개 사례, 같은 oracle, 같은 채점기, 같은 호출 상한(decision 2회·retrieval 2회)에서 비교한다.
기준선 결과는 `eval/v1/results/heuristic.json` 에 먼저 고정한다.

**JEV가 이겼다고 말할 수 있는 조건 (전부 충족):**
1. macro yield(V-2)가 기준선보다 **+0.10 이상** 높다
2. macro precision(V-3)이 기준선보다 낮지 않다
3. `must_not_claim` 사례의 근거 0건(V-4)이 유지된다
4. 안전 기준 4개가 전부 0건이다
5. retrieval 총합(V-6)이 기준선보다 많지 않다

**"비겼다"**: yield 차이가 ±0.10 이내. 이 경우 추가 호출의 비용·지연만 늘었다고 보고한다.
**"졌다"**: yield가 낮거나, 위 3·4번 중 하나라도 무너지면 즉시 패배로 기록한다. 안전 항목은 성능으로 상쇄되지 않는다.

비용 판단은 별도로 적는다: 실제 호출 후에만 지연·토큰·요금을 기재하고, 그 전에는 `not_measured` 로 둔다.
**채점기나 사례가 바뀌면 이 비교는 무효다.**

## 7-A. 강한 코드 기준선 (부록 — 최초 사전등록의 일부가 아니다)

> **표기 경계.** 이 절은 좁은 기준선(`DeterministicHeuristicSelector`)의 성적이 이미 측정된 **뒤에**,
> 사용자 지시로 추가됐다. 원래 §7의 사전등록에 포함돼 있었다고 소급해 말하지 않는다.
> 보고할 때는 **좁은 기준선 대비 결과와 강한 기준선 대비 결과를 나란히** 적는다.

### 왜 추가하는가

좁은 기준선은 셀 후보만 고르도록 구현돼 있다. 제품·유형 후보를 고를 수 있는 JEV와 비교해
"JEV가 더 낫다"고 말하기에는 상대가 약하다. 그래서 **같은 후보·같은 상태·같은 상한**만 쓰는
코드 기준선을 하나 더 두고, JEV가 그것까지 이겨야 모델을 쓸 실익을 말할 수 있게 한다.

좁은 기준선의 기존 결과(macro yield 0.3718, FAIL)는 **그대로 실패로 남긴다.** 지우거나 대체하지 않는다.

### 규칙 (측정 이전에 고정 — 결과를 본 뒤 조정하지 않는다)

`GreedyEvidenceSelector`. 입력은 JEV에 줄 것과 동일하다: `EvidenceState.view()` 스냅샷과
서버가 만든 후보 목록. **oracle을 읽지 않는다. 사례 ID로 분기하지 않는다. 난수를 쓰지 않는다.**

1. **적격 후보**: `group_delta >= NOISE_FLOOR_DELTA` 이고 `available_tickets >= MIN_ADMITTED_TICKETS` 인 후보.
2. **집중 판정으로 넓은 후보를 떨어뜨린다**: 셀이 아닌 후보(제품·유형)는, 적격한 셀 후보 중에
   `cell.group_delta >= CONCENTRATION_RATIO × broad.group_delta` 인 것이 하나라도 있으면 제외한다.
   근거: 증가의 대부분이 한 셀에 몰려 있는데 제품·유형 전체를 조회하면, **증가하지 않은 그룹의 문의**가
   근거 목록에 섞인다. 그것은 이 시스템이 막으려는 오독을 스스로 만드는 일이다.
   증가가 여러 셀에 퍼져 있을 때만 넓은 후보가 살아남는다.
3. **남은 후보 중 `available_tickets` 가 가장 큰 것**을 고른다. 동률이면 `group_delta` 가 큰 것,
   그다음 `candidate_id` 오름차순. 근거: 후보가 제공하는 정보 중 확보 가능한 근거량의
   유일한 대리 지표가 pool 크기다. delta 순으로 고르면 문의가 거의 없는 셀에 걸린다.
4. 남은 후보가 없으면 `DEFER`.
5. 2차 조사에도 같은 규칙을 적용한다 (서버가 이미 조사한 필터를 후보에서 뺀다).

`CONCENTRATION_RATIO = 0.70`. "증가의 대부분이 한 셀에 몰렸다"의 조작적 정의다.
0.5로 두면 두 셀에 반씩 나뉜 경우까지 집중으로 보고, 0.9로 두면 사실상 모든 경우에 넓은 후보를 허용한다.
**이 값은 측정 전에 한 번 정하고, 결과를 본 뒤 바꾸지 않는다. 측정은 1회다.**

### 판정

강한 기준선도 §6.1·§6.2의 같은 기준(S-1..S-4, V-1, V-4, V-2 최소선 0.40)으로 채점한다.
실패하면 실패로 보고한다. 특히 이 규칙이 §6.2 V-4(함정 사례에서 근거 0건)를 깨면,
"근거량 최대화가 연관·인과 경계를 무너뜨린다"는 결과로 기록한다.

### JEV 주장 수위 (사전 등록)

| JEV가 이긴 상대 | 말할 수 있는 것 |
|---|---|
| 좁은 기준선만 | **"좁은 휴리스틱보다 개선"** — 그 이상은 아니다 |
| 좁은 기준선 + 강한 코드 기준선 | **"모델을 쓸 실익이 관측됨"** |
| 아무도 못 이김 | 추가 호출의 비용·지연만 늘었다고 보고한다 |

승리 조건 5개(§7)는 **각 기준선에 대해 따로** 적용한다.

### 이 8개 사례의 성격 (정직 표기)

C08은 데이터 실측을 본 뒤 개정됐다(개정 1). 따라서 이 8건은 **독립적인 미공개 시험 성적이 아니다.**
"held-out benchmark", "사전에 봉인된 시험지" 같은 표현을 쓰지 않는다.
이것은 **선택 정책을 비교하기 위해 저자가 구성한 진단용 사례 모음**이며, 그렇게만 소개한다.

## 7-B. v1.1 — 서버 근거 채택 규칙 보강 (사후 안전 보정)

> **표기 경계.** 이것은 v1.0 사전등록 결과의 **대체가 아니라 사후 안전 보정**이다.
> v1.0에서 측정된 두 기준선의 결과는 그대로 보존하고, 아래 경계에서 각각 **한 번씩** 재측정한다.
> 재측정값을 v1.0 값과 바꿔치기하지 않는다. 두 세대를 나란히 보고한다.

### 무엇이 드러났는가

강한 코드 기준선이 C05에서 근거 72건을 제시했다. selector가 넓은 제품 후보를 골랐고,
그 문의들이 **출처·날짜·필터·본문 라벨 검사를 전부 통과했기 때문**이다.
검증기는 그 문의가 *실제로 증가한 세부 그룹*에 속하는지를 보지 않았다.

이 구멍은 selector의 문제가 아니라 **서버의 문제**다. 이 경계를 selector(또는 JEV)의 보류 판단에
맡기면 이 프로젝트의 핵심인 "선택은 모델, 근거 채택은 서버"가 약해진다.

### v1.1에서 바뀌는 것 (시스템 규칙 하나)

**증가를 설명할 근거로는 증가한 세부 그룹의 문의만 채택한다.**

- 검증기는 각 문의가 속한 `(제품, 불만 유형)` 셀이 **비교 구간에서 delta > 0** 인지 확인한다.
  아니면 근거로 승격하지 않고 거부 사유와 함께 기록한다.
- 이 검사는 **일반 규칙**이다. 사례 ID 분기, C05 전용 예외, oracle 참조를 쓰지 않는다.
  증가한 셀의 집합은 서버가 이미 계산한 지표에서 온다.
- 넓은 제품·유형 조회 자체는 계속 허용한다. 막는 것은 조회가 아니라 **승격**이다.
- 이 검사는 생략할 수 없다. 검증기 호출부에서 기본값으로 건너뛸 수 있는 형태로 두지 않는다.

### 바뀌지 않는 것

8개 사례, oracle, 지표 정의, 임계값(V-2 최소선 0.40 포함), 호출 상한(decision 2·retrieval 2),
두 기준선의 selector 규칙 — **전부 그대로다.** 바뀌는 것은 서버의 근거 채택 경계 하나뿐이다.

### 재측정 절차

1. v1.0 결과를 `eval/v1/results/heuristic_v1_0.json`, `eval/v1/results/greedy_v1_0.json` 로 보존한다.
2. 두 기준선을 각각 **1회씩** 재측정한다. 결과를 본 뒤 규칙을 조정하지 않는다.
3. v0의 24개 평가 결과가 바뀌는지 확인한다. **바뀌면 안 된다** — v0의 heuristic은 셀 후보만 고르고
   셀 후보는 정의상 delta > 0 인 셀이므로, 이 규칙은 v0에서 아무것도 거부하지 않아야 한다.
   바뀐다면 그것은 이 규칙이 일반 규칙이 아니라는 신호이므로 보고한다.

### 예상되는 부작용 (미리 적어둔다)

이 규칙이 들어가면 채택된 문의는 구조적으로 "delta > 0 셀의 문의"가 되고,
oracle의 `useful_ticket_ids` 도 같은 조건을 포함하므로 **V-3 precision 은 다시 1.0에 가깝게 고정**된다.
즉 v1.1에서 precision 은 변별력이 거의 없다. 변별하는 지표는 **V-2 yield, V-4, V-5, V-6** 이다.
이것은 규칙이 옳게 작동한 결과이지 지표를 유리하게 만든 조작이 아니다 — 미리 적어두어 사후 해석을 막는다.

### JEV

JEV 비교는 **v1.1 경계에서** 수행한다. §7·§7-A의 승리 조건과 주장 수위는 그대로 적용하되,
비교 상대는 v1.1에서 재측정한 두 기준선이다.

## 7-C. JEV adapter — 공식 문서로 확인한 형상과 실행 잠금

문서 확인일: 2026-09-22. 확인하지 못한 것은 "미확인"으로 남기고 추측해 만들지 않는다.

### 확인된 형상

- 모델 식별자 `typesafe-ai/jev`. **채팅 모델이 아니라 평가(evaluation) 모델이다.**
  `messages` 가 없고 산문을 내놓지 않는다. OpenAI 호환 엔드포인트에서는 **지원되지 않는다.**
- `POST https://ai-gateway.vercel.sh/v1/evaluate`, `Authorization: Bearer $AI_GATEWAY_API_KEY`.
  본문은 `model` + `state` + `questions`. 응답은 `answers` + `usage` + `providerMetadata.gateway.cost`.
- 질문 유형은 `boolean` / `choice` / `score`. **우리 결정은 `choice` 하나로 표현한다** —
  선택지는 서버가 만든 후보 ID들과 `DEFER`, 설명문도 전부 서버가 쓴다.

이 형상은 이 프로젝트의 경계와 우연히 잘 맞는다. 모델이 **자유 텍스트·검색어·SQL을 낼 수 있는 통로가
애초에 없다.** 돌아오는 것은 선택지 하나와 확률뿐이다.

### 확률의 취급

응답의 `probabilities` 는 **기록만 한다.** 정답 확률로도, 실행 권한으로도 쓰지 않는다.
임계값을 두어 자동 판단에 쓰지 않는다. Controller의 fail-closed 처리는 그대로다 —
후보 밖 값·형식 오류·예외는 전부 DEFER로 강등하고 위반으로 기록한다.

### 재현성 (미리 적어두는 한계)

`/v1/evaluate` 에 **seed 가 문서화돼 있지 않다.** `temperature`·`max_tokens` 는 엔드포인트 메타데이터의
`supported_parameters` 에는 있으나 평가 요청 예시에는 없어 **미확인**으로 둔다.
따라서 JEV 측정은 **재현 불가능한 단일 표본**이다. 재시도 0회 예산에서는 분산을 측정할 수 없다.
그러므로 결과는 *탐색적 관측*으로 보고하고, 단일 표본으로 "개선했다"를 단정하지 않는다.
승패 조건(§7·§7-A)은 그대로 적용하되, 통과하더라도 **표본 1회라는 사실을 함께 적는다.**

### 실행 잠금 (사용자 조건)

1. 예산: **8사례 × 최대 2회 = 총 16회.** 재시도·추가 확인 호출 **0회.**
   어댑터가 자체 카운터로 상한을 강제하고, 초과 시 호출하지 않고 예외를 던진다.
2. 실호출은 **명시적 플래그 + 유효한 API 키**가 모두 있을 때만 일어난다. 기본값은 호출하지 않음이다.
3. **실행 직전 가격 재확인이 통과해야 한다.** 유료로 바뀌었거나 가격을 확인할 수 없으면
   자동 실행하지 않고 비용 승인을 다시 받는다.

### 2026-09-22 가격 확인 결과 — **조건 미충족, 자동 실행 금지**

공식 페이지에서 확인된 것은 **유료**다: 모델 페이지 `$0.042/1M input tokens`,
공개 메타데이터 `pricing.prompt = 0.000000042`, `completion = 0`, `discount = 0`.
**무료 표기도, 프로모션 필드도, 종료일 필드도 없다.** 게이트웨이는 마크업을 붙이지 않는다.
"2026-09-25 무료 종료"라는 표기는 **제3자 페이지에서만** 확인됐고 vercel.com 에서 재현되지 않았다.

따라서 §7-C 잠금 3번 조건이 발동한다 — **비용 승인을 다시 받기 전에는 실호출하지 않는다.**
(참고 산술: 공식 요율 기준 16회 총 비용은 매우 작다. 그러나 조건은 금액이 아니라 절차다.)

미확인으로 남은 것: Jev의 free-tier 포함 여부, free-tier 수치 한도,
`/v1/evaluate` 의 `temperature`/`max_tokens` 수용 여부, 스트리밍·타임아웃·state 크기 상한, 공식 Python 예제.
