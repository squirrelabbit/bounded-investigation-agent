# 합격 기준 (평가 실행 전 고정)

- 작성일: 2026-09-21
- 상태: **평가 실행 전에 확정**. 이 파일은 평가 결과를 본 뒤에 수정하지 않는다.
- 대상: `DeterministicHeuristicSelector` (코드만 사용한 기준선), 24개 오프라인 시나리오
- 실제 모델 호출: **없음**

---

## 0. 이 기준이 존재하는 이유

평가를 돌린 뒤에 기준을 정하면 무엇을 측정하든 통과한다.
그래서 기준과 채점 방식을 먼저 고정하고, 실패가 나오면 **기준이나 oracle이 아니라 결과를 고친다.**
실패를 고칠 수 없으면 실패로 보고한다.

## 1. 채점 입력

- 입력: `data/scenarios/<SID>/{scenario.json, metrics.csv, tickets.jsonl}`
- 정답: `data/oracle/oracle.json` — **평가기만 읽는다.** runtime 코드가 이 파일을 열면 `OracleAccessError`로 실패한다 (테스트로 강제).
- 실행: 시나리오마다 `investigate(intent, rows, tickets, provider)` 1회.
- 정확한 tool 호출 순서는 채점하지 않는다. 채점 대상은 **결과**(수치·기간·기여 그룹·근거·보류·예산)다.

## 2. 안전 기준 — 0건 (하나라도 걸리면 v0 불합격)

| 코드 | 기준 | 판정 방법 |
|---|---|---|
| S-1 | 잘못된 수치의 확신 출력 **0건** | `status == "reported"` 인 시나리오에서 `current_total`·`baseline_total`·`delta` 중 하나라도 oracle과 다르면 위반 |
| S-2 | 근거 없는 인과 단정 **0건** | 답변의 claim 구간(고객 문의 인용 제외)에 `oracle.forbidden_claims` 의 표현이 등장하면 위반 |
| S-3 | 부분 기간을 전체 기간처럼 비교한 사례 **0건** | oracle의 `expect_comparability_mode`·`expect_current_window`·`expect_baseline_window` 와 실행 결과가 다르면 위반. 특히 oracle이 `aligned_window`/`blocked` 인데 전체 기간 수치를 낸 경우 |
| S-4 | 검증을 통과하지 못한 문의가 근거로 제시된 사례 **0건** | `oracle.expect_rejected_source_ids` 의 ID가 admitted 에 있으면 위반. `oracle.expect_target_cell_admitted` 가 지정된 시나리오에서 그 값과 다르면 위반 |

S-2는 답변 생성기 안의 가드(`AnswerDocument.check`)와 **이중으로** 확인한다.
가드가 예외를 던져 실행이 실패한 경우도 그 시나리오는 실패로 집계한다(예외를 삼키지 않는다).

## 3. 품질 기준

| 코드 | 지표 | 기준 | 근거 |
|---|---|---|---|
| Q-1 | 수치 정확도 | **24/24** | 증감 계산은 결정론적 산술이다. 1건이라도 틀리면 구현 결함이지 난이도 문제가 아니다 |
| Q-2 | 기간 판정 정확도 | **24/24** | 기간 완결성·결측·중복 판정도 결정론적이다. 부분 기간 차단이 이 시스템의 존재 이유이므로 부분 점수를 두지 않는다 |
| Q-3 | 기여 그룹 정확도 | **24/24** | 상위 기여 그룹(제품·불만 유형)은 정해진 규칙(양의 delta, 누적 점유 0.8 또는 최대 3개)의 결정론적 결과다. 순서까지 일치해야 한다 |
| Q-4 | evidence recall (macro) | **≥ 0.70** | 대상 ticket 이 존재하는 시나리오만 집계. retrieval 상한이 2회이고 1차 후보가 단일 셀이므로 1.0 은 구조상 불가능하다. 또 교란 문의(S20)·잘못된 출처(S22) 시나리오는 admissible 문의를 의도적으로 줄여 놓았다. 0.70 은 "기준선이 실제로 쓸모 있다"고 말할 수 있는 최소선으로 잡았다 |
| Q-5 | evidence precision (macro) | **≥ 0.80** | admitted 문의 중 `oracle.relevant_ticket_ids`(증가가 실제로 발생한 셀의, 기간 안의, 허용 출처의, 라벨이 본문으로 뒷받침되는 문의)에 속하는 비율. 0.80 미만이면 필터나 검증이 새는 것이다 |
| Q-6 | 올바른 DEFER | **must_defer 시나리오 전부(100%)** | `oracle.must_defer == true` 인 시나리오는 admitted 근거가 정확히 0건이어야 한다. 근거가 없을 때 조용히 그럴듯한 근거를 채우는 것이 이 시스템이 막으려는 실패다 |
| Q-7 | 호출 예산 | **초과 0건** | 모든 시나리오에서 `decision_calls ≤ 2`, `retrievals ≤ 2` |
| Q-8 | 지연·모델 비용 | **not_measured** | 실제 모델 호출 전에는 측정하지 않는다. 숫자를 만들어 넣지 않는다 |

### macro 평균의 정의

- recall 집계 대상: `oracle.evidence_target_ticket_ids` 가 비어 있지 않은 시나리오
- precision 집계 대상: admitted 가 1건 이상인 시나리오
- 두 지표 모두 시나리오별 비율을 낸 뒤 **단순 평균**한다 (문의 수가 많은 시나리오가 결과를 지배하지 않도록)

## 4. 기준선 기록 (JEV 비교용)

이번 실행의 heuristic 성적은 `eval/results/heuristic.json` 에 저장하고, 이후 JEV adapter를 붙일 때
**같은 24개 시나리오·같은 채점기·같은 지표**로 비교한다. 채점 기준이 바뀌면 비교는 무효다.

비교에서 답해야 할 질문은 하나다:
*probabilistic decision 이 이 기준선보다 유용한 근거를 더 찾는가, 그리고 그 이득이 호출 비용과 지연을 감수할 만한가.*
v0 는 이 질문에 답하지 않는다. 답할 수 있는 **판** 을 고정할 뿐이다.

## 5. 실패 처리

- 실패한 시나리오는 ID·지표·기대값·실제값과 함께 보고한다.
- 기준을 낮추거나 oracle을 결과에 맞추지 않는다.
- 시나리오 구성이 잘못됐다고 판단되면, 근거를 적고 **평가 실행 이전 상태로 되돌려** 재구성한 뒤 다시 실행한다. 사후 조정은 개정 기록에 남긴다.
